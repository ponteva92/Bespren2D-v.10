# Bespren Defense Art Plan — Towers, Traps, Utilities, Base Core

Scope: raise the eight Tier-1 structure cards (`T1_KINETIC`, `T1_CHEMICAL`, `T1_ELECTRIC`, `T1_SUPPORT`, `T1_BARRICADE`, `T1_LANDMINE`, `T1_SLOWING_PIT`, `T1_RAZOR_SNARE`) and the Base Core camp to premium mobile-readable quality inside the existing 480x270 / Mobile-renderer / zoom-0.38 / 64px-grid contract. This plan does not touch enemy presentation (`docs/overhaul/ENEMY_ROSTER_PLAN.md` territory) or world terrain/scatter (`docs/overhaul/WORLD_VARIETY_PLAN.md` territory).

## 0. Brief-vs-code discrepancies (code wins)

- **Source paths.** The task frame refers to `src/game/structure_catalog.gd` and siblings. The domain actually lives under `src/tactical/`: `structure_catalog.gd`, `structure_definition.gd`, `tower_combat_profile.gd`, `placed_structure_2d.gd`, `tower_targeting_controller_2d.gd`, `tactical_build_system.gd`, `grid_placement_controller_2d.gd`. `src/game/` only holds `combat_state_coordinator.gd`, `day_night_cycle.gd`, `game_world.gd`, `player_avatar.gd`. All citations below use the real `src/tactical/` paths.
- **"One canonical shared render stage" is not true of structures today.** The task brief points at `tools/art/render_polyhaven_district_sprites.py` as the shared stage. That script is real and matches the brief's description (EEVEE, `film_transparent`, Freestyle silhouette, `AgX - Medium High Contrast`, exposure 1.48, three DISK area lights named `WARM_KEY`/`COOL_RIM`/`SOFT_FILL`, oblique orthographic camera) — but the camp and all eight structures are **not** baked through it. They come from a third, independently-drifted script, `tools/art/generate_camp_and_structure_sprites.py`, which shares the EEVEE/Freestyle/orthographic/AgX family resemblance but has its own fixed light rig (`"BSP Warm Key"` at energy 1050, `"BSP Cool Rim"` 820, `"BSP Soft Fill"` 540 — different names, positions, and energies from the district rig), no auto-exposure (confirmed absent by grep: no `exposure =` assignment anywhere in the file), and no auto-framing (hand-picked fixed `ortho_scale` per asset: camp `9.2`, the three towers plus Support `5.4`, Barricade `6.8`, the three traps `4.8`; see `generate_camp_and_structure_sprites.py:407-415`). A **fourth-and-newest** rig, `tools/art/aaa_bake_rig.py`, exists for imported low-poly GLBs and deliberately rejects AgX in favor of Godot's `Standard` view transform, with an in-code comment explaining why: `"Standard, not AgX: the A/B/C probe showed AgX desaturates the locked semantic anchors (cyan tech read as blown white, foliage read as olive)"`. That is exactly the Electric tower's cyan (`#31E6E6`/`#00FFFF` family) and the Chemical tower's toxic-green identity. Section 4 resolves this tension; it is not safe to assume the district script is a drop-in "reuse this" answer for combat-critical color readability.

- **Mipmap filter requested but never baked.** `placed_structure_2d.gd:361` sets `_structure_visual.texture_filter = CanvasItem.TEXTURE_FILTER_LINEAR_WITH_MIPMAPS` on every structure sprite, but every one of the nine current `.import` files (`assets/2d/structures/*.png.import`, verified on `base_camp_topdown.png.import` and `structure_t1_kinetic.png.import`) has `mipmaps/generate=false`. ## 1. Honest audit — what the current pipeline actually produces

`tools/art/generate_camp_and_structure_sprites.py` (669 lines) is fully self-contained and reproducible down to the pixel: isolated `BESPREN_CAMP_STRUCTURE_STAGE` scene, deterministic material set (22 named materials, e.g. `BSP_Structure_Amber` emission 3.2, `BSP_Structure_Cyan` emission 3.0, `BSP_Structure_Violet` emission 3.0, `BSP_Structure_Red` emission 2.6), EEVEE + `film_transparent` + Freestyle (`line_thickness=1.3`, lineset thickness authored per asset - `1.45` default against `2.7` for the camp) + `AgX - Medium High Contrast`, 320x320 output, and a checked-in `generated_asset_manifest.json` recording generator SHA-256 and per-file byte counts/hashes. That discipline is real and should be preserved regardless of what else changes.

**Corrected, 2026-09-06.** Four claims in the paragraph above were stale or wrong when checked against the source, and they are worth naming because three of them were true when written and rotted silently. The file is 669 lines, not 441. The stage is `BESPREN_CAMP_STRUCTURE_STAGE`; `BESPREN_SPRITE_STAGE` belongs to the *character* generator, so the citation named the wrong script's scene. There are 22 distinct `BSP_` materials, not 17. And the lineset thickness is a per-asset column rather than a single `1.45`. The fourth is the one that mattered: it made a deliberate authored contract look like a global constant.

The reproducibility wording is also now stronger than "genuinely reproducible", because the claim it replaced was actively misleading. `write_generated_asset_manifest.py` used to record that "EEVEE is not bit deterministic", citing three runs producing three digests. Three runs do produce three digests - but at an identical byte count, and decoding them shows byte-identical IDAT streams and a max per-channel delta of exactly 0 across all 102,400 pixels. The digests differ only because Blender stamps a wall-clock `Date` and a measured `RenderTime` into PNG `tEXt` chunks. The old phrasing licensed the wrong conclusion: it made a rebake whose pixels had genuinely drifted look like expected noise. A rebake of unmodified source must match the shipped pixels exactly, and any non-zero delta is a regression to explain rather than absorb.

The geometry itself is the weak link, and it is worth being blunt about why. Every structure is assembled from `_cube()`, `_cylinder()`, `_sphere()`, `_cone()`, `_torus()` primitive helpers (`generate_camp_and_structure_sprites.py:58-178`), each finished with a single `BevelModifier` of width `0.03`-`0.06` (`_finish()` at line 58). A 0.03-0.06 bevel on a primitive is edge-softening, not surface detail — there is no boolean cutting, no greeble, no secondary silhouette break, no panel-line or bolt/rivet language anywhere in the script. Six of the eight structures (`_build_kinetic`, `_build_chemical`, `_build_electric`, `_build_support`) share one literal `_base_plate()` — a charcoal cylinder plus a rust torus ring (`generate_camp_and_structure_sprites.py:204`) — so at a glance several cards are "a slightly different blob on the identical charcoal-disc-with-rust-ring base." That repetition is efficient but is the single biggest reason the current set reads as CAD-primitive placeholder rather than authored hardware: nothing in the base communicates "salvaged," only the emissive top module differs.

Two additional concrete problems, both confirmed above, both fixable independent of any geometry rework:
1. The mipmap import/filter mismatch (Section 0) — currently undermines minified-texture quality at actual gameplay zoom.
2. No auto-exposure or auto-framing — the nine `ortho_scale` values are hand-tuned once and will silently drift out of frame or under/over-expose the moment anyone edits `_build_*()` geometry without re-tuning by eye, unlike the two newer rigs which converge automatically.

The prior `docs/VISUAL_ASSET_OVERHAUL_AUDIT.md` (2026-08-15) already signed off on this set as meeting a lower bar — "eight distinct top-down Blender silhouettes... separately color-, shape-, and mechanic-coded," backed by `artifacts/structure_visual_library.png` and the smoke-test uniqueness check. That verdict is not wrong on its own terms: `tests/smoke_test.gd`'s `_validate_structure_visual_library()` (lines 341-381) does assert eight unique texture paths and does pass. But "eight unique files" and "distinct at a large contact-sheet render" are a materially lower bar than "premium and legible at the ~37-54 logical-px sizes players actually see in a 480x270 viewport at zoom 0.38" (Section 5). The existing `tests/structure_visual_render_validation.gd` contact sheet additionally applies its own `scale = Vector2.ONE * 0.56` multiplier on top of each structure's internal scale (line-referenced in that file's `POSITIONS`/scale setup) — i.e. the one GPU gate that visually proves structure art renders structures noticeably *larger* than real gameplay ever will. That gate is good for catching gross regressions (missing texture, wrong material) but is not evidence of AAA+ legibility at true size. Section 6 proposes closing that specific gap.

Base Core (`base_core.tscn`) is a partial exception: it already carries a triple-shader runtime stack (`volumetric_aura.gdshader` aura, `toon_emissive_outline.gdshader` on `Core`, `base_scale_glow.gdshader` on `GlowSilhouette`) plus a non-shadow-casting `PointLight2D`, all layered on top of the same `base_camp_topdown.png` source render the eight structures share the pipeline with. The presentation layer is doing real work to elevate the camp; the underlying silhouette (a primitive-cube canvas shelter — see `_build_camp` calls at lines 178-179, e.g. `"Shelter dark entrance"`, `"Shelter amber seam"`, both plain beveled cubes) is subject to the identical placeholder critique as the structures. Raising the camp further should spend the budget on the *source silhouette*, not on a fourth shader — CLAUDE.md §10 already has 0 shadow-casting lights and 1 full-screen pass fully committed elsewhere.

## 2. Per-structure art direction

At that size only one strong silhouette read, 1-2 value zones, and a single accent color/shape marker survive — everything below proposes exactly one such feature per structure rather than a detail list.

A cross-cutting rule worth adopting explicitly: **towers keep saturated, "live weapon" accent color; traps stay desaturated/environmental except for one small saturated tell-light.** This is not fully true today (Landmine/Slowing Pit/Razor Snare accents — `c65b44`, `8f8064`, `d86a9d` — are already fairly muted per `structure_catalog.gd`, which is good) but should be locked as a rule so future cards don't erode it.

## 3. State presentation

The runtime overlay system already lives in `placed_structure_2d.gd:412` (`_draw()`) and `:457` (`_draw_attack_presentation()`), driven by a fixed `ATTACK_TRACE_SECONDS = 0.18` (line 23). What exists today, per state:

- **Idle** — base sprite only, range/health overlays drawn but attack trace inactive. Present and working.
- **Acquiring** — there is no distinct visual between "idle, no target" and "target just acquired, about to fire." The aim-direction line (drawn in `_draw()` for towers with automatic attack) appears the instant a lock exists; there is no telegraphed "spooling up" cue before the first shot. **This is a real gap**, not a nitpick — a half-second wind-up tell (e.g. the muzzle/coil emissive ramping from resting to full brightness via the existing `accent_strength` shader uniform, tweened, no new draw calls) would let players read "that tower is about to fire" before it does, which matters more at 39px than a fancier idle pose would.
- **Firing** — fully implemented and kind-specific: `_draw_attack_presentation()` switches on `_attack_trace_kind` — CHEMICAL gets an expanding green burst circle per target, ELECTRIC gets a zigzag `_draw_electric_arc()` polyline per target, LANDMINE/SLOWING_PIT get expanding rings from origin, RAZOR_SNARE gets an X-slash cross plus an accent-color "snap" arc, KINETIC (default) gets a simple line+dot tracer. This is good, kind-differentiated work already in the codebase. One thing worth checking rather than assuming: `ATTACK_TRACE_SECONDS = 0.18` is roughly 11 frames at 60 FPS but only 5-6 frames at the documented 30 FPS fallback (CLAUDE.md §10) — worth a look on a throttled device to confirm it doesn't read as a single-frame flicker rather than a trace.
- **On-cooldown** — no distinct visual found between "just fired, reloading" and "idle, ready." A lightweight cooldown tell is cheap to add because the infrastructure (a secondary thin bar, or a pulsing/dimming reuse of the existing `accent_strength` uniform) already exists for the health bar in the same `_draw()` pass; it should only render while `cooldown_remaining > 0` so it doesn't add a permanently-visible new UI element.
- **Depleted** — confirmed precisely at `take_damage()` (`placed_structure_2d.gd:221-232`): on `current_health == 0` it calls `stop_tower_combat()` and emits `depleted`, then `queue_redraw()`. There is no destruction flash, no scorch mark, no debris — whatever removes the node happens outside this file in response to the signal. For a "decay tells history" game (CLAUDE.md §2) a destroyed tower currently leaves nothing behind. A brief (~0.2-0.3s) fade-out plus a small pre-baked scorch decal left at the position would pay off that pillar; flagging it as a scope/cost decision (Section 7) since a persistent decal is one more Node2D per destruction and needs a cap/pool discussion, not a free addition.
- **Trap armed / triggered / spent** — Landmine and Slowing Pit/Razor Snare diverge here. Landmine is `consumed_on_attack = true` and calls `retire_after_attack_trace()` (referenced in Section 1's file read) — it vanishes right after its 0.18s blast rings finish, with no lingering scorch mark, the same missed "decay tells history" opportunity as tower depletion. Slowing Pit and Razor Snare are reusable/persistent, so their open need is the same as a tower's missing cooldown tell: a clear "is this armed and ready, or still cycling" signal, ideally the identical lightweight pulse-fade approach so the whole defense roster shares one cooldown-tell language instead of inventing a second one.
- **Security light** is correctly withheld from Barricade and all three traps already (`_build_security_light()`, `placed_structure_2d.gd:392-394`: `if structure_id == StructureCatalog.T1_BARRICADE or (_definition != null and _definition.is_trap()): return`) — traps and the wall should not glow at night, and they don't. No change needed there.

Net: firing presentation is already strong and kind-differentiated; acquiring, cooldown, depletion, and trap-spent presentation are the real gaps, and all four can be closed with the existing shader uniforms and `_draw()` overlay system — no new shader, no new geometry required for any of them.

## 4. Pipeline decision: keep, replace, or hybrid

Three bake rigs exist in the codebase today, not one:

| Rig | View transform | Auto-exposure | Auto-framing | Light rig | Palette discipline | Currently used for |
|---|---|---|---|---|---|---|
| `generate_camp_and_structure_sprites.py` (current structures/camp) | `AgX - Medium High Contrast` | None — fixed | None — hand-picked `ortho_scale` per asset | 3x DISK: Warm Key 1050 (1.0,0.62,0.26), Cool Rim 820 (0.16,0.58,0.62), Soft Fill 540 (0.42,0.46,0.41) | 17 ad-hoc named materials, no locked table | Camp + 8 structures, primitive geometry only |
| `render_polyhaven_district_sprites.py` ("canonical" per task brief) | `AgX - Medium High Contrast`, exposure 1.48 base | Per-asset convergence, `target_luma` default 70.0 | Auto: `ortho_scale = exact_span * max(framing_scale, 1.16)` | 3x DISK: `WARM_KEY` 980 (1.0,0.62,0.30), `COOL_RIM` 790 (0.18,0.52,0.58), `SOFT_FILL` 700 (0.48,0.50,0.45) | None — assumes pre-textured imported GLTF | Imported Poly Haven CC0 district props |
| `aaa_bake_rig.py` (newest) | `Standard` — explicitly **not** AgX, in-code rationale documents an AgX desaturation regression on cyan tech and foliage | Auto, `target_luma = 104.0`, iterative metering | Auto: `_frame_subject()`, pad `1.16` | 3x SUN: `AAA_KEY`/`AAA_FILL`/`AAA_RIM` | `BESPREN_PALETTE`, 21 locked entries via `BSP_<KEY>` material naming | Newest imported low-poly GLB content (the direction `WORLD_VARIETY_PLAN.md` is standardizing on) |

The task brief's framing — "reuse the canonical shared stage" — is not the safe default here. `render_polyhaven_district_sprites.py` is built to import and photograph *pre-textured* GLTF assets, not to author new hand-built primitive geometry from scratch, and it carries the same AgX Medium High Contrast look that `aaa_bake_rig.py` was written specifically to move away from because it desaturates cyan and green — exactly the two colors Electric and Chemical need to sell their identity (Section 2). Copying the district rig's recipe verbatim for new tower art risks reintroducing the regression the newest rig already fixed.

**Recommendation: hybrid, anchored on `aaa_bake_rig.py`'s infrastructure, not a wholesale asset-source swap.**

1. Keep `shaders/sleek_sprite_finish.gdshader` exactly as-is. Read in full: it is `render_mode unshaded`, one base texture sample plus four neighbor taps for the outline (five total reads), a luminance/saturation/contrast grade, two `smoothstep` masks (shadow lift, highlight accent), one diagonal sheen term, and one final palette-cohesion mix — zero loops, zero extra passes, already shared across every structure and every environment atlas in the project. The presentation layer is not the problem; the source geometry feeding it is. No shader work is needed here.
2. Do not keep the primitive-only, no-auto-anything recipe in `generate_camp_and_structure_sprites.py` as the long-term source of truth — Section 1 already established why its output reads as placeholder, and its lack of auto-exposure/auto-framing makes every future edit fragile.
3. Do not blindly adopt `render_polyhaven_district_sprites.py` either, for the AgX-desaturation reason above, and because it is architecturally built around importing existing assembled GLTF props (`AssetBake` dataclass, modular `ObjectInstance` compositing), not around lighting hand-built primitive collections.
4. Rebuild the camp and eight structures on `aaa_bake_rig.py`'s auto-exposure (`target_luma=104`) + auto-framing (`_frame_subject`, pad `1.16`) + `Standard` transform + `BESPREN_PALETTE` retargeting infrastructure. This keeps the *authoring* style the same (hand-built Blender primitives are fine in principle — cheap, deterministic, no licensing questions — the problem in Section 1 is effort/detail, not the primitive technique itself) while converging the whole project onto one bake philosophy instead of three, and removing the AgX cyan/green risk for Electric and Chemical specifically. This is new engineering work (the rig currently targets imported GLBs, not hand-authored collections) but is a bounded, mechanical port, not a rewrite of the render philosophy.
5. For the "reads as placeholder" geometry problem itself, add a small amount of real hard-surface reference/greeble rather than trying to sculpt more detail freehand. Two license-clean sources were verified in this pass:
   - `Addons/[AR] Post-Apocalyptic - Starter Pack/3. Models/{dae,fbx}/` (Atomic Realm, license confirmed in Section 0: commercial/non-commercial use and editing allowed, no redistribution) has directly relevant low-poly props already sitting in `dae`/`fbx`: `electric_pole_1` (Electric tower mast language), `metal_board_1`/`metal_board_2`/`metal_board_3` (Kinetic armor-plating greeble), `wall_spiked` and `wooden_spike_barricade` (Barricade). Import a handful of these through a **new dedicated immutable workshop `.blend`**, mirroring the exact precedent already set by `bespren_local_environment_workshop.blend` and `bespren_polyhaven_district_workshop.blend` — same review discipline, same license-evidence recording, no exception to CLAUDE.md's "no destructive `Addons/` changes without confirmation" rule since this is read-only import.
   - Poly Haven CC0 models, verified live against `https://api.polyhaven.com/assets?type=models` on 2026-09-02 (521 total models fetched and filtered by keyword — these IDs exist today, they are not guesses): `propane_tank`, `small_lpg_tank` (Chemical tank reference), `portable_generator`, `modular_electricity_poles`, `modular_industrial_pipes_01`, `modular_pipes`, `modular_electric_cables` (Electric/Support greeble), `old_military_crate`, `wooden_military_crate`, `plastic_crate_01`/`02`/`03` (Support/camp), `can_rusted` (small rust detail). None of these are downloaded or promoted yet — they are candidates for the same fetch → workshop → bake → manifest pipeline `tools/asset_pipeline/fetch_polyhaven_models.py` already implements (browser User-Agent required, confirmed working; it hits `/info/<id>` and `/files/<id>` and records SHA-256 per file).
   - Explicitly **not** recommended: `Addons/Godot-4-Tower-Defense-Template-master` (MIT-licensed, confirmed via its root `LICENSE` file, by "Alp," 2024). Its `Assets/turrets/` PNGs (`technoturret.png`, `laserturret.png`, `reallaser.png`, `dynamite.png`, `dynamite-pack.png`) were opened directly — `technoturret.png` renders as a tiny, low-fidelity flat icon-style sprite, not a hard-surface source, and does not match Bespren's rendered-then-baked pipeline at all. At best a rough behavioral read reference, not an asset source. `Addons/PostApocalypse_AssetPack_v1.1.2` (TheLazyStone, `LICENSE.txt` confirmed: free non-commercial, $2 USD minimum commercial, no redistribution) is a 2D character/enemy sprite-sheet pack with no structure-relevant hard-surface content — out of scope for this document.
6. Base Core: spend the improvement entirely on `_build_camp()`'s source silhouette (Section 2's tent-ridge-plus-mast-spike direction). Do not add a fourth runtime shader or a shadow-casting light — CLAUDE.md §10's budget (1 full-screen pass already spent on weather, 0 shadow-casting 2D lights) leaves no headroom, and the camp already gets more runtime presentation than any structure card.

## 5. Texture memory budget

Current state, confirmed from `assets/2d/structures/*.png.import` (`compress/mode=0` = Lossless, i.e. full RGBA8 uploaded to VRAM with no BPTC/ETC2 compression; `mipmaps/generate=false` = no mip chain baked — **since superseded: all nine now generate mipmaps, so the `4.69 MiB` row below is the shipping figure**) and `generated_asset_manifest.json` (exact per-file byte counts) and the render script's `resolution_x = resolution_y = 320` (`generate_camp_and_structure_sprites.py:336-337`):

| Item | Value |
|---|---:|
| Source render resolution | 320 x 320 RGBA8 |
| Raw VRAM per texture (320x320x4 bytes) | 400 KiB |
| Structure/camp texture count | 9 (camp + 8 structures) |
| Current total raw VRAM (no mip chain, since `mipmaps/generate=false`) | 3,600 KiB ≈ 3.52 MiB |
| Current total on-disk PNG size (sum of manifest `bytes` fields) | 611,176 bytes ≈ 597 KiB |
| Proposed: enable `mipmaps/generate=true` to match the code's existing `TEXTURE_FILTER_LINEAR_WITH_MIPMAPS` request (standard ~1.33x chain overhead, matching `WORLD_VARIETY_PLAN.md`'s own convention) | 400 KiB × 1.333 ≈ 533 KiB/texture × 9 ≈ 4,800 KiB ≈ **4.69 MiB total** |
| Worst-case simultaneous on-screen defenses (rough upper bound for this Tier-1 scope, ~30 structures + camp) | ~30 × 533 KiB ≈ 15.6 MiB — trivial against typical mobile VRAM budgets |

Two deliberate calls, stated with reasoning rather than by default pattern-matching the rest of the project:

- **Enable mipmaps, don't shrink the source resolution.** At ~37-54 logical px on-screen (Section 2), a 320px source is genuinely oversampled (roughly 6-8x), which is exactly what you want for clean minification *if* mips are actually baked — it is currently wasted supersampling because they are not (Section 0). Fixing the `.import` setting is a few-KB-per-texture cost for real antialiasing quality; shrinking the source would save an amount of VRAM (a few hundred KiB total) that is not meaningful at mobile scale and would remove headroom for the greeble pass in Section 4.
- **Do not atlas-pack the structure set.** The environment pipelines (local/Poly Haven/Hidden Alley district) atlas because they place hundreds of small instances and atlasing cuts draw-call/texture-bind overhead at that population. Structures are placed in the dozens at most per session; atlasing nine textures saves negligible VRAM (VRAM cost is dominated by total pixel area, not file count) and would only pay off in reduced texture binds, which is not a demonstrated bottleneck here. Revisit only if profiling on real Android hardware shows otherwise.
- **Disk-size guardrail.** Adding hard-surface greeble detail will make the renders less flat, which typically compresses somewhat worse; budget a generous +50% ceiling on the current 597 KiB (≈ 900 KiB total) for the reworked nine files. That is still negligible against the `Bespren-runtime-polish.pck` (5,737,388 bytes) and `Bespren-polish.apk` (34,394,814 bytes) totals CLAUDE.md §12 already tracks.
